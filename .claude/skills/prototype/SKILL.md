GaeGGUL Defence의 prototype 스킬을 옮긴 것이다. 원본은 별도 git 워크트리에서 돌렸지만,
Unity는 폴더마다 Library를 새로 만들어야 해서 여기서는 **같은 프로젝트 안의 분리된 폴더**를 쓴다.

## 1. 질문 정하기
아이디어에서 프로토타입이 답할 질문 하나를 뽑는다. 흐릿하면 질문을 먼저 문장으로 확정한다.
예: "수건 미니게임을 스와이프 방식으로 바꾸면 3초 안에 끝낼 수 있나?", "손님 50명이면 길찾기가 30fps를 유지하나?"

## 2. 계획 (만들기 전에 보여 주고 확인)
3~5줄로:
- 질문
- 답하는 데 필요한 최소 코드
- 생략할 것(오류 처리, 연출, 저장, 구조)
- 시간 상한(반나절~하루)

## 3. 만들기
"`Assets/Prototypes/[이름]/`에 만들까요?"라고 묻고 승인하면 시작한다.
- 스크립트·씬·프리팹 모두 이 폴더 안에. 씬은 `Assets/Prototypes/[이름]/[이름].unity`로 새로 만들고 EditScene은 건드리지 않는다.
- 스크립트 맨 위:
  ```csharp
  // PROTOTYPE - NOT FOR PRODUCTION
  // Question: [질문]
  // Date: YYYY-MM-DD
  ```
- 네임스페이스는 `Bathhouse.Prototypes.[이름]`으로 감싸 본 코드와 이름 충돌을 막는다.
- 기준은 일부러 낮춘다: 수치 하드코딩, 임시 그래픽, 오류 처리 생략, 가장 단순한 방법.
- 본 코드(`Assets/Scripts/`)의 클래스를 **수정하지 않는다**. 필요하면 복사해서 프로토타입 폴더에서 고친다.
- 본 코드는 프로토타입을 참조하지 않는다.
- 작업판에 `lane set --task "프로토타입: [이름]" --hold "Assets/Prototypes/[이름]/**"`로 잡아 둔다.

컴파일 오류가 본 게임까지 막지 않도록, 만든 뒤 에디터 Console(또는 `Docs/harness/tools/unity.md`의 batchmode 확인)로 컴파일을 확인한다.
측정할 수 있는 것(시간, fps, 성공률, 시도 횟수)은 기록한다.

## 4. 리포트
```markdown
# 프로토타입: [이름]
## 질문
## 만든 것 (걸린 시간, 생략한 것)
## 결과 (관찰한 사실 — 느낌이면 구체적으로: "탭 반응이 0.2초 늦게 느껴짐")
## 측정
## 판정: 진행 / 수정 / 폐기
(근거 한 문단)
## 진행한다면
- 본 구현에서 달라져야 할 구조, 성능 목표, 범위 조정, 예상 작업량
## 배운 것
```
"`Assets/Prototypes/[이름]/REPORT.md`에 저장할까요?"라고 묻는다.

## 5. 마무리
질문, 결과, 판정, 리포트 경로를 요약한다.
- **진행**: `/quick-design`로 본 구현 변경 메모를 쓴다. 본 구현은 프로토타입 코드를 옮겨 다듬지 말고 새로 쓴다.
- **수정**: 바뀐 질문으로 다시 `/prototype`.
- **폐기**: 리포트가 결과물이다. 폴더를 지울지 사용자에게 묻는다(지울 때는 `.meta`까지).
작업판은 `lane done --note "[판정]"`으로 정리한다.

GaeGGUL Defence의 quick-design 스킬을 옮긴 것이다. 이 프로젝트에는 시스템별 GDD가 없으므로
**현재 코드와 SO 값, 시스템 카드**를 기준 문서로 삼는다. 결과는 `Docs/design/quick-specs/[이름]-YYYY-MM-DD.md`.

## 1. 분류
인자를 읽고 하나로 분류해 사용자에게 확인받는다(인자가 없으면 무엇을 바꿀지 묻는다).
- **수치 조정**: 동작은 그대로, 숫자만 (예: 월세 주기, 미니게임 제한 시간, 일차별 손님 수, 시설 수익)
- **동작 수정**: 새 상태 없이 기존 동작을 조금 바꿈 (예: 탕을 안 거쳐도 때밀이 가능)
- **기능 추가**: 기존 시스템에 상태·상호작용 1~2개 추가 (예: 새 말풍선 종류, 새 상점 아이템)
- **작은 새 시스템**: 일주일 안쪽의 독립 기능 (예: 업적 팝업, 일일 목표)

여러 시스템을 크게 바꾸거나 일주일을 넘을 것 같으면 그렇게 말하고, 범위를 나눌지 묻는다.

## 2. 현재 상태 확인 (초안 전에 반드시)
1. `python Tools/harness/harness.py resolve "<변경 내용>"`으로 카드를 찾고 읽는다.
2. 바뀔 값·규칙이 실제로 어디 있는지 찾는다. 수치면 SO 클래스(기본값)와 실제 `.asset` 값을 **둘 다** 읽는다(에셋 값이 우선).
3. `Docs/design/quick-specs/`에 같은 시스템을 건드린 이전 메모가 있으면 읽고 모순을 피한다.
4. 찾은 것을 보고한다: "현재 값은 `Assets/Data/MiniGameData.asset`의 baseTimeLimit = 10, 규칙은 `MiniGameBase.StartMiniGame`. 이전 메모 없음."

## 3. 초안

### 수치 조정
```markdown
# 변경 메모: [제목]
- 종류: 수치 조정 | 시스템: [카드 이름] | 날짜: YYYY-MM-DD

| 값 | 위치(에셋·필드) | 현재 | 변경 | 이유 |
|----|-----------------|------|------|------|

## 영향 계산
(일차별로 어떻게 달라지는지 표. 예: 1/3/5/10일차 제한 시간, 일일 순수익)

## 수락 기준
- [ ] 에셋 값이 [변경값]
- [ ] [어느 상황]에서 차이가 보임
- [ ] [관련 동작]이 그대로
```

### 동작 수정 / 기능 추가
```markdown
# 변경 메모: [제목]
- 종류: 동작 수정 | 기능 추가 | 시스템: [카드] | 날짜: YYYY-MM-DD

## 요약
(1~2문장: 무엇을 왜)

## 현재 동작
(코드 근거: `Class.Member`, 파일:줄)

## 바뀐 동작
(프로그래머가 이 글만 보고 구현할 수 있을 만큼 정확하게. 새 상태·새 수치는 범위까지)

## 영향받는 곳
| 시스템/파일 | 영향 | 할 일 |

## 수락 기준
- [ ] 
- [ ] 회귀 없음: [깨지면 안 되는 기존 동작]
```

### 작은 새 시스템
```markdown
# 변경 메모: [제목]
- 종류: 작은 새 시스템 | 날짜: YYYY-MM-DD | 예상 구현: N시간

## 개요
(언제 켜지고 무엇을 만드는지 한 문단)

## 규칙
(순서는 번호, 조건은 글머리표)

## 조정값
| 값 | 기본 | 범위 | 이유 |
모든 조정값은 SO로 둔다(코드에 하드코딩하지 않는다).

## 연결
(어떤 GameManager 이벤트를 구독하는지, 저장이 필요하면 GameData 어느 필드인지)

## 수락 기준
- [ ] 
```

## 4. 저장
전체 초안을 보여 주고 "`Docs/design/quick-specs/[kebab-제목]-YYYY-MM-DD.md`에 저장할까요?"라고 묻는다.
승인하면 폴더를 만들고 저장한다. 새 시스템이면 시스템 카드를 새로 만들지도 묻는다.

## 5. 넘기기
저장 후: 파일 경로, 종류, 시스템, 바로 구현할지를 알려 준다.
구현으로 넘어가면 이 메모의 수락 기준을 그대로 확인 항목으로 쓴다.
